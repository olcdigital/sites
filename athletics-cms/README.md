# Athletics CMS — Phase 1 Prototype

A real, running instance of the CMS from the mockups: an admin app and a public site, both reading from the same SQLite database, proving the architecture from `data-model.md` and `roadmap.md` actually works end to end.

## Why Flask instead of Next.js/Prisma

The original plan. The sandbox this was built in blocks npm registry access entirely (`host_not_allowed` on every package, not just Prisma), so building on Next.js wasn't possible here. Flask + Jinja2 were already available (pre-installed), and SQLite is Python's standard library — so this is what's real and running right now, with zero external dependencies beyond Flask itself. The schema, the multi-tenant model, the roles/permissions system, and the block-based page renderer are all exactly what's specced in `data-model.md` — only the language/framework changed. Porting this to Next.js/Prisma later is a rewrite of the presentation layer, not a redesign; the schema in `schema.sql` maps table-for-table to `prisma/schema.prisma` if you want to see that translation.

## Running it

```
pip install -r requirements.txt
python3 seed.py     # builds dev.db fresh with Northfield College sample data
python3 app.py       # starts at http://127.0.0.1:5050
```

Then open:
- `/admin` — the CMS (hardcoded as logged-in Sarah Jennings, Admin role — real login isn't built yet, see below)
- `/site/northfield-college` — the public home page, rendered from real `pages`/`page_blocks` rows
- `/site/northfield-college/teams/mens-soccer` — the Men's Soccer team page, same renderer, different blocks

## What's real

- **The Schedule system is fully built out** — this is the one module that's no longer read-only. `/admin/opponents` is real CRUD against the `opponents` table (used as a dropdown, never typed freeform, so results stay accurate — each opponent record can carry city/state/website/logo, auto-loaded when picked). `/admin/schedule` supports adding, editing, and deleting games — including marking a game Final with a score, which sets `score_finalized_by='manual_entry'` the way the live-stats spec expects manual entries to be tagged. The season dropdown filters by whatever seasons actually exist in the data. Win/loss/tie logic is centralized in one `result_letter()` helper so a tie game can't silently render as a loss anywhere in the app.
- **Schedule is its own dedicated public page, separate from Roster** (`data-model.md` §12) — every team gets a `/site/<school>/teams/<team>/schedule` page (auto-routed through the existing generic page route, no team-specific routing code), distinct from the team hub page. The hub page keeps a compact "Upcoming Games" teaser block (plain ascending-date list, always simple regardless of the team's view configuration) that links out to the full Schedule page — the `full_page` flag on the `schedule` block type is what tells `render_block()`/`site_page.html` which of the two to render. Roster still renders inline on the team hub page only, with no dedicated page or view system of its own yet — that's designed to work the same way eventually, just not built in this pass.
- **Six school-centric schedule views, built as blocks, not standalone pages** — Classic Athletics, Matchup Cards, Compact List, Timeline, Calendar, and Season Story, all centered on the client's own team ("at Ridgeview College" / "vs. Eastmoor University") rather than a neutral, both-sides-equal scoreboard. Each view is a `<div class="sched-view">` inside the normal `.section` block on the Schedule page — same header, same theme CSS variables, same chrome as every other block — so switching views never leaves the site's design. The whole schedule block is also deliberately narrower than the page (a centered `.sched-narrow` column, ~720px), matching how most college athletics sites actually lay a schedule out rather than stretching it edge-to-edge — Classic Athletics in particular was refreshed into a plain row list with a small day/month date chip, closer in spirit to a typical Sidearm-style schedule page. Per team, Schedule Settings (`/admin/schedule`) sets a **Default View** (what a first-time visitor sees) and which of the six views are **enabled** for the public switcher (always includes the default; a team with only one enabled view gets no switcher at all — see Cross Country). There's no per-view logo option: Compact List is always text-only (the plain, dense option, by design) and every other view always shows the opponent logo, resolved automatically from the `opponents` record — never assigned per game — falling back to a two-letter initials monogram (`initials()`) instead of a broken image when an opponent has no logo on file. The visitor's own view choice is remembered client-side via `localStorage`, scoped to the whole site by school slug rather than per-team, so picking Timeline on one team's schedule carries to the next team's schedule too, without ever overriding the client's configured default on first load.
- **Every game, in every view, opens a detail card on click** — Classic rows, Matchup cards, Compact List rows, Timeline entries, individual games inside a Calendar day cell, and Season Story's next-game/upcoming/postseason entries all share one `openGameCard()` modal (see `site_page.html`'s bottom `<script>`), reading from a small per-block `window.ALL_GAMES` lookup embedded as JSON rather than a per-game page or a network round-trip. The card shows date/time, location, event group, result, and — new surface for fields that already existed on `games` but weren't rendered anywhere before — Tickets, Watch (livestream), Box Score, and Opponent Site links, whichever are present for that game. Clicking the underlined opponent name itself still goes straight to the opponent's own site instead of opening the card (`event.stopPropagation()` on that one link).
- **Proven team-agnostic, across all four teams**, each deliberately configured differently to exercise the whole system: Men's Soccer has all six views enabled (the thorough test case) with a Matchup Cards default; Women's Soccer has three views enabled; Volleyball defaults to Season Story (its postseason Event Group games spotlight correctly there); Cross Country has exactly one view enabled (Compact List, place-finish results) — the edge case that proves the switcher correctly disappears when there's nothing to switch between. Same `render_block()` code, same admin screen, just different `team_id`s and different `teams.default_schedule_view` / `enabled_schedule_views` values.
- **Time can be a specific clock time, All Day, or TBA — never a silent fourth "just blank" state.** `games.time_type` (`specific` | `all_day` | `tba`) drives this: the Event Details section has clickable All Day/TBA buttons next to the Time input that disable/clear it, and the form won't submit with `time_type='specific'` and an empty time field (client-side required check, `admin_game_form.html`). `game_time_info()` returns "All Day"/"TBA" as the display string everywhere a game's time shows — the public schedule views, the Game Location/Client School/My Location toggle (which degrades cleanly since there's no UTC instant to convert), the game detail card, and the admin schedule table. Cross Country's meets are seeded as TBA (weather/heat-dependent starts, a real pattern for that sport); the Men's Soccer alumni exhibition game is seeded All Day.
- **State (or Country)** — the location field's label makes clear it's not US-only; an away game at a foreign opponent just gets a country typed into the same free-text field. Label-only change, no schema change (the column was already freeform text).
- **Game Setup is now grouped into sections** (`/admin/schedule/new`, `/admin/schedule/<id>/edit`) — Event Details, Opponent & Venue, Coverage & Tickets, Additional Links & Files, and Results, matching the grouping discussed for the eventual Results Center split. Same fields, same field names, same JS behavior as before (team/opponent-driven auto-fill, neutral-host toggle, result-type-driven score vs. finish-place fields) — this pass only reorganizes the layout so a long form reads as five short ones instead of one long, busy one. The Results section also carries a disabled, clearly-labeled placeholder for the stats-XML import that's planned next ("Upload & Fill In Results") — not wired to anything yet, just reserving its spot in the workflow.
- **The dashboard's game-day widget is Today's Games, not a generic "upcoming games" list** (`/admin`) — every game across every team on one date (real current date by default, `?date=` steps to any other day, with Prev/Next/Today nav), each non-final game getting an inline results-entry form right there: score fields for score-based teams, Finish Place/Total Teams for place-finish teams (Cross Country), a Save Final button that POSTs to `/admin/schedule/<id>/quick_result` and marks the game Final with `score_finalized_by='manual_entry'` — the same tagging the full Edit Game form uses — plus the same disabled "Upload XML" placeholder as the full form's Results section. A final game just shows its result badge and an Edit link instead. The top stat tile still counts all upcoming games school-wide, a separate number from what's showing in the table.
- **Game Type & Neutral Host** (`data-model.md` §5c) — every game carries a required Game Type (Scrimmage / Exhibition / Non-Conference / Conference / Postseason). Scrimmages and exhibitions are excluded from the record, and so is a Neutral Host game (two outside teams playing at the client school's facility, entered with a second opponent via `opponent_two_id`) — all three are enforced by one shared `counts_toward_record()` predicate used everywhere a record gets tallied, so there's no risk of the exclusion being reimplemented (and forgotten) somewhere else. The seed data includes a Men's Soccer exhibition game and a Volleyball Neutral Host game specifically to prove both stay out of the Record Bar.
- **Time Zones** (§5d) — every game has its own `time_zone`, defaulting to the client school's configured `default_timezone` but editable per game with no automatic location-guessing. `game_time_info()` computes the site-zone time, the client-school-zone time, and a UTC instant per game; the public schedule has a Game Location / Client School / My Location toggle (server-rendered for the first two, computed client-side via `Date.toLocaleTimeString` for "My Location," since the visitor's zone is only knowable in the browser).
- **Record Bar & Alternative Results Formats** (§5e) — Schedule Settings has an on/off toggle for the Record Bar (W-L, Pct., Conference W-L, Conference Pct., Home/Away/Neutral, Streak, Last 10 — all computed live by `compute_record_bar()`, never stored) and a Results Format switch per team: Traditional Score, or Team Finish (Place) for sports like Cross Country and golf, which renders "3rd of 12 Teams" instead of a score. Individual games can also be marked No Team Score or No Result independent of that format. Cross Country is seeded with all of it: a 1st-of-8 finish, a 3rd-of-12 finish, a No Team Score meet, a No Result (upcoming-but-blank) meet, and an upcoming Conference Championship — and has its Record Bar switched off, since place-finish sports don't have a W-L record.
- **Location/Facility split & Opponent Display Overrides** (§5f) — Location is City/State; Facility is the specific venue name, kept as a separate field. Picking an opponent auto-loads its saved name/website/city/state/logo, and the display name and website can be overridden for one specific game without touching the opponent's saved record — the logo is deliberately never overridable, so it can't drift from the real opponent. This is how the "load the host school, relabel it as the invitational" workaround stays supported without corrupting master opponent data; the seed data has a Women's Soccer game against Ridgeview College displayed as "Fall Kickoff Classic."
- **Event Groups** (§5g) — a separate `event_groups` table lets several independently-scored contests (a tournament, an invitational, a quad meet) share one public header while each game keeps its own opponent, result, game type, and record eligibility. Manage them at `/admin/schedule/events`; the seed data groups two Volleyball postseason games under "Empire Conference Tournament."
- **Deliberately not built in this pass**: the Master Schools Database (§5a — a shared cross-school opponent directory with alias-matching) and the Schedule paste-import wizard (§5b — pasting a full schedule from Excel/Sheets with unmatched-opponent gating). Both are designed in `data-model.md` but are separate, larger tooling from "the schedule" itself, so they were scoped out of this build. The same is true of most of what's specced in later rounds but not yet built into this running prototype: the fuller Event Details extras beyond what Game Setup's new "Event Details" section already covers (§5h), the fuller Coverage & Tickets fields — Radio/TV, video-stream provider — beyond the Tickets/Livestream URLs the new "Coverage & Tickets" section already covers (§5i), the unified Additional Links & Files / `game_resources` system beyond the single linked-gallery field the new "Additional Links & Files" section already covers (§5j), the standalone Results Center dashboard (§5k), the Media & File Library (§13), and individual public player bio pages (every player still only shows up inline on their team's roster block — there's no player detail page or stable player URL yet, unlike a real athletics site). All of those remain design-only in `data-model.md`/`core-systems.md`. (The Results section's stats-XML import placeholder mentioned in earlier rounds is no longer just a placeholder — see Live/Box Score Stats below.)
- **The full schema** — every table from `data-model.md`'s Phase 1 scope: schools, roles/permissions, users, teams, athletes/roster_entries, opponents, games, staff_members, articles, galleries/media_assets, sponsors, pages/page_blocks. Live-stats fields exist on `games` as nullable columns, unused, so Phase 3 won't need a breaking migration.
- **Multi-tenancy** — every query filters by `school_id` (or a foreign key that traces back to one), exactly as designed. There's only one school seeded right now, but the isolation is structural, not assumed.
- **Roles & permissions** — `roles`/`permissions`/`role_permissions` are real tables with real rows (Admin/Manager/Staffer, seeded with the default permission sets from `data-model.md`), not a hardcoded if/else.
- **The block renderer** — this is the important one. `/admin/pages` lists real `pages` rows; each page's `page_blocks` rows get pulled and rendered by `render_block()` in `app.py`. A `hero` block reads its own JSON content; a `roster_grid` block looks up real `roster_entries` for whatever `team_id` is in its config. This is the actual mechanism behind "one CMS, unique public site per school," not a mockup of it.
- **The Season data model** — Athletes and Roster Entries are already split as separate tables, so the season-rollover design (a player upgrading years without duplicating) is structurally possible, even though the rollover screen itself isn't built yet.
- **Roster admin CRUD is now real** (`/admin/rosters`) — same shape as Schedule's build: a season dropdown (filters by whatever seasons actually exist in `roster_entries` for that team, newest first) and full add/edit/remove. Adding a player has two modes, toggled with the same pill-button pattern as Time's All Day/TBA: **New Athlete** creates a fresh `athletes` row plus one `roster_entries` row together, and **Existing Athlete** picks a person already in the school's athlete records and only adds a new `roster_entries` row pointing at them — the mechanism a multi-sport athlete or a returning player needs, without ever duplicating their person record. The picker shows each athlete's current team/season affiliations as context (not a hard block) so an admin can spot an accidental duplicate. Editing always updates the linked athlete's bio fields and the roster assignment together (identity's already fixed by then), and — since Team and Season are genuinely editable on that form — doubles as a lightweight manual season-rollover/transfer tool until a dedicated rollover screen exists. Removing a player only deletes their `roster_entries` row; the `athletes` person record is left alone, exactly like Schedule's delete only touching one row.
- **Fixed a real season-filtering gap while building the above**: `render_block()`'s `roster_grid` query used to pull every `roster_entries` row ever made for a team, with no season filter at all — harmless while every team had exactly one season on file, but the moment admin CRUD makes `season` an actively multi-valued, editable field (which it now is), that would have started showing athletes from every past season mixed together on the public roster. It now defaults to the most recent season on file for that team. This is a correctness fix to the *existing* public rendering, not new design — the actual public Roster page redesign (multi-view system, "standard table" + something more creative) is still explicitly deferred, see below.
- **A standalone Players directory** (`/admin/players`) — the mental model is "the `athletes` table is a real school-wide player directory, and `roster_entries` are just the assignments pinned to it," not "a player only exists inside whichever team's roster created them." The directory lists every athlete on file with a client-side search box and their current team/season affiliations; each name opens a profile page (`/admin/players/<id>`) with one bio-edit form (updates that person everywhere they appear, not per-team), a full roster history table across every team and season with Edit/Remove per assignment (reusing the same `/admin/rosters/<id>/edit` and `/admin/rosters/<id>/remove` routes Teams & Rosters uses — both routes now accept an optional `next` field so this reuse lands back on the profile instead of a team's roster list), a "+ Add to a Roster" dropdown that jumps straight into Existing Athlete mode on the roster form with that person pre-selected, and a Danger Zone that permanently deletes the player record (cascading every roster assignment with it, `ON DELETE CASCADE`) with an explicit confirm spelling out what that removes.
- **Paste Import for rosters** (`/admin/rosters/import`, linked from Teams & Rosters) — paste a whole roster in one go instead of adding players one at a time: one player per line, tab- or comma-separated, a documented column order (name, jersey, position, class, height, weight, hometown, high school), trailing columns optional, an accidental header row auto-detected and skipped. Nothing is written on paste — it goes to a review screen first with every field editable (so a misaligned column can be fixed before saving) and, critically, checks every pasted name against the **school's entire athlete database** (not just the target team), the same cross-team concern the Existing Athlete picker handles one player at a time. Any name match gets flagged with a Same Player (Merge) / Different Player (New) toggle — defaulting to Merge only when there's exactly one unambiguous match, defaulting to New (never silently auto-merged) when there's no match or more than one — before Confirm Import commits everything. Merging reuses the existing `athletes` row and only adds a `roster_entries` row; re-running the same import a second time (or importing someone already on that team/season) is a no-op rather than creating a duplicate spot, checked against `(athlete_id, team_id, season)`.
- **`roster_entries` gained a Bats/Throws field** — optional free text, sport-specific (baseball/softball, mainly), left blank for sports where it doesn't apply, same pattern as the sport-agnostic free-text Position field. `athletes.previous_school` is now labeled Previous School(s) with a semicolon-separated hint rather than adding a whole new table for what's still just free text in this prototype.
- **Bio is now two fields, not one** — `athletes.bio_text` is the Master Bio (general facts, shared everywhere that person appears) and `roster_entries` has its own separate `bio_text` for that specific sport/season, so a multi-sport athlete can have a soccer write-up that differs from their volleyball one instead of one bio trying to cover everything. Both fields live in the same roster form; the form field for the roster-level one is deliberately named `roster_bio_text` (not `bio_text`) so the two textareas in one `<form>` don't collide and silently save only one of them — a real bug caught and fixed while wiring this up, not a hypothetical one.
- **(Superseded — see below)** An earlier pass added a per-team `roster_entries.status` alongside `athletes.status` to fix a cross-team rollover bug (marking someone Graduated on one sport's roster was incorrectly pulling them off a second sport's roster too, since both checked the same person-level flag). Direct feedback in the very next round removed the concept of player status entirely — see "There is no player status field any more, on either table" below, which is the current, real behavior.
- **Rosters and Schedules can each be marked "Current" per team**, and the left-nav links to a landing hub instead of guessing. `teams.current_roster_season` / `current_schedule_season` are explicit, nullable overrides — nothing requires setting them, since every read falls back to "the most recent season on file for that team" when they're unset (`_resolve_current_season()`, one shared helper used by both the admin routes and the public renderer, so the admin's "Current" badge and what the public site actually shows can never disagree). Clicking **Teams & Rosters** or **Schedule & Results** in the sidebar now opens a card-grid hub (`/admin/rosters`, `/admin/schedule` with no query params) showing one card per team — its *current* roster/schedule only — instead of silently landing on whichever team happened to be first. This was a direct fix for how easy the old setup made it to edit the wrong sport by accident. Clicking a card opens that team's normal detail/edit view, which now also shows a "Current" badge or a "Mark as Current" button next to the season picker. The hub has two more tabs for reaching older, non-current data: **Browse by Sport** (pick a team, then pick which of its seasons to open) and **Browse by Season** (pick a season, then pick which team's roster/schedule to open for it) — both are just the same `/admin/rosters` and `/admin/schedule` routes branching on `view=`/`team=`/`season=` query params, so every existing internal link (which always passes `team=` explicitly) keeps working exactly as before.
- **Fixed a second, previously-latent season-filter gap while wiring up Current**: the public Schedule page's `full_page` query had no season filter at all — `WHERE games.team_id=? ORDER BY games.date`, every game a team ever had, regardless of season. Harmless only because no team had accumulated more than one schedule season yet; the moment a second season exists, it would have shown every season's games mixed together on one page. It now resolves the team's current schedule season the same way Rosters does, and filters to just that season.
- **Paste Import now has a reverse: Export CSV** (next to Paste Import on Teams & Rosters) — downloads the current team/season's roster in the exact same column order Paste Import expects, so it round-trips (export from one team/season, paste into another) or opens straight in a spreadsheet.
- **A player's identity got noticeably thicker.** New on `athletes`: NIL Shop Link (a single URL to a player's personal NIL shop), and a Miscellaneous group on the Player Profile — Nickname, Name Pronunciation, Academic Major, Birthdate (all optional free text; nothing in Phase 1 does calendar math on Birthdate). Also new: `athlete_social_links`, a real one-to-many table (not fixed columns) so a player can list any number of platforms — X, Instagram, TikTok, Facebook, YouTube, Threads, Snapchat, or Other — each as its own row, added/removed from the Player Profile page.
- **`teams.roster_template` finally does something.** The column (and the admin callout referencing it) already existed, but no query ever actually branched on it — every team's public roster rendered identically regardless of what it said. Roster Settings on Teams & Rosters now sets it for real, with three varieties: **Card** (the original compact number-tile grid), **Photo** (larger photo-forward tiles using each player's real headshot when they have one on file, falling back to an initials monogram — reusing the same fallback pattern Schedule already uses for opponents with no logo — with a JS `onerror` handler so a broken image URL degrades to the same fallback instead of a broken-image icon), and **Table** (the plain, dense roster table). Social links and the NIL Shop link render as small badges under a player's name on Card and Photo (skipped on Table, which stays data-dense on purpose). This is a per-team admin choice, not a public visitor-facing switcher like Schedule's six views — a lighter mechanism was enough for what was asked for here, and a full switcher remains an option later if you want visitors themselves to be able to toggle it.
- **Jersey number collisions are intentionally NOT validated.** Flagged as a possible gap and confirmed this is fine as-is — common in some sports (football) to have shared/duplicate numbers on one roster.
- **The Rosters/Schedule detail screens are now single-team, on purpose.** Direct feedback: the old team-switcher tabs at the top of `/admin/rosters`/`/admin/schedule` made it too easy to end up editing the wrong sport without noticing. Once you click into a team from the hub, that screen only shows that one team — a callout says so — with a single "&larr; All Teams" link back to the hub to switch sports. Every other admin link into these screens (rollover, bulk edit, coaches, settings) stays scoped to that same team/season for the same reason.
- **There is no player status field any more, on either table.** Direct feedback: a player, once created, stays in the system forever — "active" isn't a fact worth tracking about the *person*, only about which roster(s) they're currently assigned to. `athletes.status` and the Active/Graduated/Departed dropdown are both gone. In their place, `roster_entries.hidden` is a plain per-team-per-season checkbox ("Hidden from this roster") for temporarily suppressing someone from one team's public roster without touching their record (injured, suspended, redshirt) — and Season Rollover's old three-way status pill is now a two-way Returning/Not Returning toggle: Not Returning doesn't write anything anywhere, it just means that player isn't carried into the new season's `roster_entries` on *that* team. Nothing here can ever affect a second sport's roster for the same person.
- **The roster Edit Player screen locks what it shouldn't let you change from there.** The Athlete section (name, hometown, bio, etc. — the shared person record) renders read-only with an "Edit Athlete Info" button to unlock it, since editing it from a roster screen affects every team that person is on. Team and Season are always shown as plain confirmation text, never editable dropdowns, on both Add and Edit — moving someone between rosters is Season Rollover's or the Existing Athlete picker's job, not a field to fat-finger here.
- **Adding an Existing Athlete is now a live search, not a dropdown.** A text box filters the athlete list client-side as you type, since scrolling one `<select>` stops working once a school has more than a handful of players on file.
- **Adding a brand-new player now shows the whole player profile up front** — Master Bio, Miscellaneous (nickname, pronunciation, academic major, birthdate), and Social Links, alongside the roster assignment fields for whichever roster you launched the form from (team/season pre-filled and locked, not re-picked) — instead of a thin subset of fields with everything else deferred to a separate profile-page visit afterward.
- **Height is two number inputs (feet, inches), not one free-text field**, displayed everywhere as `FT-IN` (e.g. `5-11`) — the admin table, the public Card/Photo/Table roster displays, and CSV export. Paste Import still takes height as one pasted column (a spreadsheet paste won't have two), best-effort parsed into feet/inches on commit.
- **Three Custom Fields on `roster_entries`** (`custom_field_1/2/3`), free text, with school-chosen labels set in Roster Settings — for whatever a given program wants on their roster that isn't already a field (eligibility notes, a program-specific tag, etc.).
- **Roster Settings got a lot bigger.** Per team-and-season (`roster_settings`, new table): which fields show on the public **Table** display, in what order, and under what header text (see the dedicated Field Order page below — Card/Photo keep their fixed visual layout, this is aimed at Table's column shape); a **Roster Title** that defaults to "`{season} {school} {team} Roster`" (e.g. "2025-26 Northfield College Men's Basketball Roster") with a text box to override it; a **Team Photo URL** with an inline preview, shown above the public roster; a **Display Coaches Below Roster** Yes/No; and **Sort Roster By** (Jersey Number then Last Name — the default — or Alphabetical by Last Name).
- **Field order/visibility/labels moved to their own page with real drag-and-drop** (`/admin/rosters/fields`, linked from Roster Settings) — direct feedback that a checkbox-plus-typed-order-number list was cramped for 13 fields and that reordering should be drag-and-drop, not rank numbers. Each row is a `<div draggable="true">`; plain HTML5 drag events (`dragstart`/`dragover`/`dragend`) reorder the list in the browser, and Save posts the whole thing as one JSON array (`fields_config`, now shaped `{"key","enabled","label"}` per field) rather than a pile of per-field form inputs — no external drag-and-drop library, consistent with the rest of this prototype's vanilla-JS approach. **Jersey #, Name, and Previous School are now ordinary configurable fields** (draggable, hideable) rather than pinned in place, and **every field — not just the three custom ones — can have its own custom header title**, with a blank box falling back to the app's default label for that field. Old saved settings rows (from before Jersey #/Name/Previous School existed as options, or before per-field labels existed) are backfilled automatically on read (`_roster_fields_config()`), so nothing crashes on a settings row saved by an earlier round.
- **Scheduled-publish controls hide themselves once a roster or schedule is actually live and Current.** Direct feedback: once something's published and set as the current version, the Visibility/Scheduled-Publish/Makes-Current controls are just clutter (and a small risk of re-hiding something live by accident) — so Roster/Schedule Settings now shows a short explanatory line instead of the Publishing section whenever `is_current_season and not settings['hidden']` is true, and brings the full controls back the moment either condition changes (marking a season Hidden again, or a different season becoming Current).
- **A Coaches tab lives alongside Roster Settings**, same shape as Players/roster_entries: `staff_members` is the school-wide coach directory (already existed, just unused before this), and a new `roster_coaches` join table is what actually ties one of them to one team's specific-season roster — so a coaching change between seasons doesn't rewrite history. Each attachment can be marked Head Coach (exactly one expected per team/season, for coach-record tracking later) and can be Hidden from the public site without removing them from the record (a firing mid-season, say). A quick "+ Add New Staff Member" inline form covers a school with no staff on file yet, same pattern as New Athlete on the roster form.
- **Rosters and Schedules can be Hidden until published, with an optional scheduled go-live.** Per team-and-season, independent of Current: a future roster/schedule can exist and be fully built out in the admin without being visible on the public site yet. Roster/Schedule Settings has a Visibility toggle plus an optional Scheduled Publish datetime, with a choice of whether going live also promotes that season to Current. This prototype has no background job runner, so publishing is applied lazily — a `before_request` hook checks on every request whether any scheduled publish time has passed and flips it live right then (see `_apply_due_publishes()` in `app.py`); functionally indistinguishable from a real cron for a demo, just implemented without one.
- **Bulk Edit** exists for both Rosters and Schedule (buttons next to Export CSV / + Add Game) — every entry's most commonly-touched fields as plain text boxes in one table, saved together in a single commit. Distinct from Paste Import, which is for adding *new* players: this is for touching several *existing* rows at once (a jersey renumbering, a batch of hometowns, a handful of final scores) without opening each one's Edit screen individually. Schedule's Bulk Edit deliberately covers only date/time/location/result, not every field the full Edit Game form has (opponent, ticket/stream links) — those still go through the individual form.

## Live / Box Score Stats (started with Football)

Explicitly scoped as a first pass, not the whole eventual feature: **team totals for a single game**, imported from a stats feed, phased toward true live updates rather than built as a real-time feed integration from day one — a real vendor connection, individual player stat lines, and season-long cumulative stats/leaders are all left for a later round.

- **This is the real mechanism behind what used to be a disabled placeholder.** Earlier rounds' Results section had a permanently-disabled "Upload & Fill In Results" button reserving its spot in the UI; `games.feed_score_for`/`feed_score_against` (nullable, unused) and `games.status` already including a `live` value were both put there for exactly this. All three are wired up for real now — nothing about this pass required a breaking migration, which is exactly why they were seeded that way originally.
- **Only surfaced for a sport that has stat categories defined.** `teams.sport` is a new canonical sport key, independent of the team's own display `name` (so renaming "Football" to something else on the public site would never break the lookup) — a new `TEAM_STAT_CATEGORIES` registry in `app.py` maps a sport key to its list of `{key, label}` categories, same shape/pattern as `ROSTER_FIELD_LABELS`. Only `football` has an entry today; every other seeded team's `sport` is set too, but since nothing maps to categories for them yet, the entire feature (Results section stats UI, Schedule Settings' Live Scoring control, admin schedule table's Stats column, the public game card's box score) simply doesn't render for them — not a disabled stub, just absent, which is the correct look for "not built for this sport yet."
- **Team totals only, on purpose** — Total Yards, Passing Yards, Rushing Yards, First Downs, 3rd Down Conversions, Turnovers, Penalties-Yards, Time of Possession for football. `game_team_stats` (new table) is one row per `(game, side, stat_key)` — deliberately EAV-shaped rather than one column per stat, so a future sport's completely different category list never needs a schema change, only a new `TEAM_STAT_CATEGORIES` entry. `side` is `for`/`against`, the same client-centric convention `games.score_for`/`score_against` already used (this is a client site, not a neutral scoreboard). Every stat value is stored and displayed exactly as the feed sends it (e.g. `"6-14"`, `"31:12"`) — never reformatted — since the feed is assumed to already format it the way it should read.
- **`teams.live_scoring_mode`, a column that already existed but did nothing until now, is what turns this on per sport.** As of the webhook pivot (see the dedicated section below) it only gates the *final* box score commit — **Off** (no stats webhook/UI at all for that team's games), **Confirm Before Publishing**, or **Publish Automatically**. A live push's score/status update always applies immediately regardless of this setting. Football seeds as Confirm Before Publishing, the safer default for a school just turning this on.
- **Import used to be the primary mechanism; it's now a manual fallback.** (`/admin/schedule/<id>/stats/import`), reachable from a game's Edit screen or the admin Schedule table's Stats column. Paste the XML into a textarea or upload a file. `_parse_stats_feed_xml()` targets the real vendor format (PrestoSports' `<fbgame>` export — see the dedicated section below); everything downstream — `game_team_stats`, the box score, the game card — doesn't care whether the XML arrived by paste or by webhook, since both paths call the same `_commit_stats_import()`/`_apply_feed_score_update()` functions.
- **A feed import never silently overwrites a human's manually-entered score.** The feed's own reported score always lands in `feed_score_for`/`feed_score_against`, but the "official" `score_for`/`score_against` only follows the feed when nothing manual has already claimed authority over it (`score_finalized_by != 'manual_entry'`) — otherwise the feed's stats still save, just without touching the score a person already confirmed by hand. Verified directly: manually setting a score, then re-importing a feed with a different score, leaves the manual score untouched while `feed_score_for`/`against` and the stat table both update.
- **The "phased toward live" part**: `games.status` can now actually be set to Live (the admin Status dropdown had never offered it before, despite the column supporting it), and a feed import maps its own reported status (`final`/`completed` &rarr; Final, `live`/`in_progress` &rarr; Live) onto the game automatically. The public game detail card shows a pulsing red **LIVE** pill with the current score, the box score table (when there's anything on file), and a "Stats updated &lt;timestamp&gt;" line — re-running an import on the same game (simulating a feed being polled again mid-game) updates all of it in place. Football is seeded with one finished game (a full 8-category box score) and one game marked Live right now (a partial box score, fewer categories filled in, exactly what a mid-game snapshot would look like) to demonstrate both ends of that arc without an actual live data source behind it.

## Live Game Center (built, then removed this round — see the pivot below)

The team-totals box score above was actually a misread of the original ask — "live stats display" turned out to mean a fan-facing, in-game experience (StatBroadcast's StatMonitr was the reference point, "but more creative"), not another admin-facing box score. A full standalone public page per game was built for this: styled like ESPN's Gamecast (score bug + play-by-play ticker + stat comparison bars), with a fixed-height four-tab app shell (**Drive**, **Plays**, **Team Stats**, **Player Stats**), a football field graphic whose ball animated down the field play by play (driven by a new `yard_line`/`down_distance` pair on `game_plays`), and 20-second auto-refresh polling.

**This entire page was removed in the next round**, on direct feedback: rather than build a real-time in-game experience in-house, the plan going forward is to partner with a real live-stats provider (StatBroadcast or similar) and focus this app's own effort on the websites themselves. `game_center.html` and its four `_game_center_*.html` partials, the `game_center`/`game_center_data` routes, and every helper that only existed to feed them (`_load_game_center_data`, `_current_drive`, `_yard_line_label`, `_bar_pct`) are all gone — `/site/<school>/games/<id>/live` now 404s. What survived: the two EAV tables it introduced, `game_plays` and `game_player_stats` (still populated by every stats-feed import, since the parser already produces them cheaply), and the player-stat-category registry (`PLAYER_STAT_CATEGORIES` — Passing, Rushing, Receiving, Defense for football). Both now serve the box score described in the next section instead of a standalone Game Center.

## The pivot: a stats-feed webhook, not a fan-facing live page

Verbatim ask that drove this round: *partner with a live-stats provider for the real-time fan experience; this app should just (1) receive live XML from stat computers to keep the schedule page's score current in real time, and (2) use the final push to generate the box score.* Three follow-up decisions were confirmed directly rather than guessed, since removing already-built functionality (the Game Center) isn't a call to make silently: remove the Game Center entirely (rather than keep or simplify it), add a real inbound webhook endpoint (rather than keep the paste/upload form as primary), and make a live push's score update always auto-apply regardless of `live_scoring_mode` (only the *final* box score commit stays gated by that setting).

- **`POST /api/stats-feed/<token>/<int:game_id>`** is the new inbound endpoint a stat-computer or provider integration pushes XML to directly — no admin has to paste anything once it's configured. `token` is a per-team secret (`teams.stats_feed_token`, `secrets.token_urlsafe(16)`, lazily generated on first use via `_get_or_create_stats_feed_token()` so existing seeded teams don't need a migration step). This is explicitly **not real auth** — it's an unguessable-URL convention, consistent with this whole prototype having no real auth system yet (see "No auth" below) — but it's enough to keep a stray request from updating the wrong team's game. A wrong token, a missing game, or a team with `live_scoring_mode='off'` all return an identical 404, so a probing request can't learn which reason applied. One token per team, shared across every game that team plays — a real integration is typically configured once per program/season, and putting the specific game in the URL avoids needing feed-side date/opponent-matching logic this prototype doesn't need yet. A "Regenerate Webhook Secret…" button on Schedule Settings rotates it (with a confirm dialog, since it immediately breaks whatever URL a provider already has on file).
- **The score/status update and the full box score commit are now two separate operations.** `_apply_feed_score_update()` is the new, small function — it writes `games.status`/`score_for`/`score_against`/`feed_score_for`/`feed_score_against` (respecting the existing manual-entry-preservation rule) and always runs immediately for every push, live or final, regardless of `live_scoring_mode`. `_commit_stats_import()` is unchanged in what it does (the full team-stats/plays/player-stats replace) but now calls `_apply_feed_score_update()` internally rather than duplicating that logic, and clears any pending review copy (see below) once it commits.
- **A final push still respects each team's Live Scoring setting — that's the one place it still gates anything.** `auto_publish`: the webhook calls `_commit_stats_import()` immediately, same as before. `manual_confirm`: the score already updated (per the point above), but the full box score doesn't commit yet — the raw XML is stashed on `games.pending_feed_xml`/`pending_feed_received_at` for an admin to review. The admin Schedule table shows an amber **Pending Review** badge, the game's Edit screen shows a callout with a link to review it, and the existing Stats Feed page (see below) pre-fills its textarea from the pending XML — reviewing and clicking **Confirm & Publish** runs through the exact same `_commit_stats_import()` path a webhook's `auto_publish` push would have taken, just with a human in the loop first.
- **The paste/upload form still exists, but it's now a fallback, not the primary path.** Relabeled "Stats Feed" (was "Import Stats Feed"), it leads with the webhook URL to hand to a provider, and the paste/upload form below is framed as a manual testing/fallback tool for when no provider is hooked up yet. Both paths funnel through the same `_parse_stats_feed_xml()` / `_commit_stats_import()` / `_apply_feed_score_update()` functions — there's no separate "webhook version" of the import logic to keep in sync.
- **The box score now displays on the public schedule/game-card, not a standalone page**, since there's no more Game Center to hold it. `_enrich_game()` (used everywhere the public schedule renders a game) now attaches `player_stats` (built by the existing `_build_player_stat_tables()`, reused as-is) and `scoring_plays` (a new `_load_scoring_plays()` batch loader, filtering `game_plays` to `is_scoring_play=1`) alongside the team totals it already carried. The existing `openGameCard()` modal (same client-side-JSON architecture as before, `window.ALL_GAMES`) renders a **Scoring Summary** list and per-category player stat tables under the team totals it already showed — no new routes, no new server-rendered partials.
- **"Scoring Summary," not full play-by-play** — the full parsed play list is still stored in `game_plays` (harmless, and the parser already produces it), but nothing displays it any more; only the scoring plays surface, both in the admin's stats-import preview and the public game card, matching how a real printed box score's "Scoring Summary" section works. A scoring play's `down_distance` is folded in as a small inline parenthetical (e.g. "(3rd & Goal)") rather than being its own column.

## The stats feed is now a real vendor format (PrestoSports)

Everything above this point was built and verified against an invented placeholder XML shape, because no real feed sample existed yet. The school then provided an actual completed-game export from their real stats provider, PrestoSports, and `_parse_stats_feed_xml()` was rewritten to parse that real `<fbgame>` format directly — same external contract (same return shape, same `StatsFeedError` behavior), so nothing downstream of it changed. This section describes the parser itself, which the webhook pivot above didn't touch — only how its output gets delivered (webhook vs. paste) and displayed (game-card box score vs. the removed Game Center) changed.

- **This is a genuine vendor format, not a guess.** PrestoSports' `<fbgame>` export nests each team's totals and every player's stat lines under `<team vh="V"|"H">`, and play-by-play under `<plays><qtr>...<play>...</qtr></plays>` — verified against a real NAIA game file (Arizona Christian at OUAZ, 10/18/2025), including spot-checks of known totals (yardage, box score lines, scoring plays) matching the parsed output exactly.
- **Nothing in the feed says which team is "us"** — PrestoSports only labels Visitor/Home. `_resolve_presto_sides()` uses this game's own Home/Away setting as the primary signal, falling back to matching the opponent's name for a neutral-site game, and raises a clear `StatsFeedError` (rather than guessing and silently misattributing a player's stats to the wrong side) if neither resolves.
- **Field position required a real coordinate conversion**, not just a passthrough — PrestoSports reports a play's spot as `"ARIZONA35"` style text (team ID + yards from *that team's own* goal line, whoever's territory the ball happens to be in), which `_presto_yard_line()` converts to this app's existing 0-100 "for"-frame `yard_line` convention.
- **Down-and-distance is built from the feed's `down`/`togo` attributes**, not sent pre-formatted — `_presto_down_distance()` produces `"2nd & 7"` or `"3rd & Goal"` text, and correctly suppresses it for PAT-attempt plays (`togo="0"` on those isn't a real down at all).
- **"Final" vs. "live" status is inferred**, not explicitly stated by the feed — a `<score final="Y">` marker (seen once, on the last scoring play of the one completed game provided) means final; its absence means live. **This is unverified against a real in-progress export** — only a final-game file has been provided so far. Re-check this logic (and clock coverage — PrestoSports only stamps a `clock` on some plays, not every one, in the sample seen) the moment an in-progress sample arrives.
- **Team/player stat mapping is a subset, on purpose** — PrestoSports reports far more than this prototype's `TEAM_STAT_CATEGORIES`/`PLAYER_STAT_CATEGORIES` registries have columns for (kicking, punting, return yardage, quarter-by-quarter scoring, an explicit drive log with real drive boundaries). Only what those registries define gets pulled; the rest of a real feed's richness is parsed by ElementTree but not carried through — same "only what the UI shows" scope as before, just against real data now. Notably, the feed's own `<drives>` block has real drive boundaries that are more accurate than this app's own `_current_drive()` same-side-plays heuristic — using them would need a schema change (a stored drive index per play) that wasn't made in this pass.
- **The shipped demo data is untouched.** The real game file was used only to build and verify the parser (direct function calls against the real XML, spot-checking known values) — `seed.py` and the Northfield College Falcons demo school/data are unchanged, so a real student-athlete's real game performance is never shown under the fictional demo school's name.

## The Story System (recaps, features, general articles, feature stories)

`articles` was already fully specced (data-model.md §7 / core-systems.md §1) and already in `schema.sql` — school/team scoping, a category, season tagging for archive filtering, `linked_game_id` for auto-recaps, `linked_gallery_id` for a photo set, and a draft/pending_review/published status — but had no admin screen and no public archive built against it until an earlier round added both. **A follow-up round then took detailed, field-by-field feedback on that first Article Editor** and rebuilt it into what's described below — release scheduling, a subheadline, Related Links, a rich-text body, sport/season association with game-linking, curated Home/Sport-page rank rotators, an editable Filename, and a Template Type placeholder. Everything in this section reflects that rebuilt version; the schema migration that went with it (`subheadline`, `hidden`, `publish_applied`, `home_rank`, `sport_rank`, `template_type` on `articles`, plus a new `article_links` child table) needed a fresh `python3 seed.py` since it changed column shape, not just added nullable columns with defaults.

- **News moved to the top of the admin left nav**, directly under Dashboard (was previously between Dashboard and Pages further down) — direct feedback that stories are used often enough to deserve top billing, not because of its position relative to Pages specifically.
- **Release scheduling is a second, independent layer on top of the existing editorial workflow, not a replacement for it.** `status` (draft/pending_review/published) is still the approval gate behind the `publish_news` permission, exactly as before. Once a story is `published`, a new **Release Date & Time** field plus a **Hold** checkbox govern when it actually goes live: set a future date and the story stays `hidden=1` until that moment, then the same lazy `before_request` hook that already handled scheduled roster/schedule publishes (`_apply_due_publishes()`) flips it visible on its own; leave the date at now/blank and Hold is a plain manual on/off switch instead. `/admin/news`'s status badge now distinguishes **Live** (green), **Scheduled** (blue, published but embargoed to a future date), **Pending Review** (amber), and **Draft** (gray) — previously it only had three states and couldn't tell a live story from a held one.
- **Subheadline** is a new optional secondary title field, shown under the headline on the article detail page and used (in place of a truncated body snippet) as the excerpt on News Archive/News-feed cards whenever it's set.
- **Related Links is a new repeatable title+URL list** (`article_links`, a new child table, delete-and-reinsert on save — same convention as the stats importer's plays/player-stats replace), rendered as a "Related Links" box on the article detail page. Links are pasted URLs for now; picking a page, document, or gallery from elsewhere on the site instead of typing a URL is explicitly future work, per the original ask.
- **The body is now a rich-text editor, not a plain textarea** — a vanilla-JS `contenteditable` + `document.execCommand` toolbar (no external editor library, same no-external-dependencies approach as the rest of this prototype) modeled on the CKEditor-style toolbar the client's reference screenshot showed: Source (raw-HTML view toggle), Undo/Redo, Bold/Italic/Underline/Strikethrough/Sub/Superscript/Remove Format, numbered and bulleted lists with Outdent/Indent, Blockquote, all four alignments, Link/Unlink, a horizontal rule, Insert Image (by URL — an upload picker needs the still-deferred Media Library), Font/Size/Text Color, H2/H3/paragraph blocks, and a Maximize toggle. The body column now stores real HTML rather than plain text split on blank lines; the article detail page renders it with `|safe` instead of the old paragraph-splitting logic, and every place a body gets used as a short excerpt (News Archive cards, News-feed blocks) now strips tags first (`|striptags`) so raw markup never leaks into a teaser. Tables and video embeds from the reference toolbar aren't built.
- **Classification replaces the old Category values** — Game Preview, Game Recap, General Article, Feature Story (previously Recap/Feature/Press Release/Announcement). This was a rename-and-restructure of the same single-select field, not an added one; `admin_game_form.html`'s "+ Add Recap" link now passes `category=game_recap` to match.
- **Sport (team) and Season are still here, but Season now auto-fills from that team's current schedule season** the moment a Sport is picked (`_resolve_current_season()`, the same helper Rosters/Schedule use for their own "Current" concept), via a `{team_id: season}` JSON map — it only fills an *empty* Season field, so it never overwrites a value already present when editing an existing story.
- **The Linked Game dropdown is now scoped to both the selected Sport and the current Season value**, not just Sport — the existing `{team_id: [...]}` JSON blob from the Add-Recap flow now carries each game's `season` too, filtered client-side on both dimensions as either field changes.
- **Story Rank on Home Page and Story Rank on Sport Page are new, and they change how both News rotators work.** Previously the home page's and a team page's "Latest News" blocks showed the 3 most recently published stories, full stop. Now each rotator is entirely hand-curated: a story only appears if it has an explicit rank number in that rotator's field (`home_rank`/`sport_rank`, nullable — blank means "off"), ordered by that number, not by publish date. This matches how a real Sidearm-style "Top Stories" module is actually curated, not auto-populated.
- **Filename is now a directly editable field** (was: an auto-generated, never-shown slug) — it auto-fills from the title as you type (same slugify-as-you-go behavior as before) until you touch it yourself, after which your edit sticks (a `filenameDirty` flag guards this), with a live `/site/<school>/news/<filename>` preview underneath. Still de-duped against the school's other articles on save to satisfy `UNIQUE(school_id, slug)`.
- **Template Type is a new placeholder field** (`template_type`, defaulting to `standard`) for which public template a story renders in — only "Standard Article" actually exists today; the field exists so more can be added later without another schema change, per the original ask ("something we will build along the way").
- **The draft/pending_review/published permission workflow itself is unchanged** — `_current_user_permissions()` still gates Publish on the `publish_news` permission the same way it did before this round; only what happens to an *already-published* story's on-site visibility timing is new (see Release scheduling above).
- **The public game card's "Read Recap" link, `_load_recaps()`, and the News Archive/News-feed system's routing, filtering, and 404-on-unpublished behavior are all unchanged** from the round that first built the Story System — this round only changed the Article Editor's fields, the storage/rendering of `body`, and how the two rotators pick what to show.
- **No image was actually attached with this round's request** despite it referencing one ("see attached image") — the rich-text toolbar above was built from the CKEditor-style toolbar description alone, then the actual reference screenshot arrived mid-build and the toolbar was checked against it directly (Source, undo/redo, the full format button set, alignment, link/image, font/size/color, and Maximize are all real matches; table insert, special characters, embeds, and the Twitter icon from that screenshot are not built).

## Story rankings: direct feedback rebuilt the Home/Sport Page rotators again

The very next round of feedback on the rank fields above changed their behavior, not just their UI — this section describes what's real now; the "Story Rank on Home/Sport Page" bullet earlier in this doc describes the version that shipped one round before this.

- **The default flipped from "off" to "by release date."** The first pass made a rotator purely curated — a story only appeared if it had an explicit rank, full stop. Direct feedback reversed that default: every eligible published story now shows by default, newest-`published_at`-first, and `home_rank`/`sport_rank` only *override* that default to pin a story ahead of the pack. Keeping a story off a rotator entirely is now its own explicit switch (`home_excluded`/`sport_excluded`, new columns) rather than a side effect of leaving rank blank — the schema migration for this (plus `home_locked`/`sport_locked`, below) needed another fresh `python3 seed.py`.
- **The Article Editor's two number inputs became dropdowns** — "Home Page Placement" / "Sport Page Placement" — with three kinds of option: "Show automatically (by release date)" (the default), a specific "Position N," or "Not shown on the \[Home/Sport\] Page." This was itself a judgment call: the feedback said the boxes "should default to 1 and probably be a dropdown (or just be sure it makes sense what it is asking)," which reads as three different suggestions rather than one spec, and the very next sentence establishes date-order as the actual default behavior — so "default to 1" was read as "the numbered options should start counting at 1" (they do) rather than "every new story's dropdown should be pre-selected to Position 1," which would just create constant rank-1 collisions across unrelated stories. Flagging this reasoning here the same way every other judgment call in this project has been flagged, in case the intent was actually the latter and a different default is wanted.
- **`/admin/news/rankings` (linked from the News Dashboard as "Manage Rankings") is the new dedicated screen for exact ordering** — a Home Page tab and a Sport Page tab (the latter needs a sport picked first, since a "Sport Page ranking" is only meaningful relative to other stories on that same team's page). It lists every eligible published story in its current effective order (pinned stories by rank, then the rest by release date — the same sort the public site itself uses) as a plain HTML5 drag-and-drop list (`admin_news_rankings.html`, same vanilla-JS reordering pattern as the Roster field-order screen, no external library), each row showing a Lock checkbox and a Remove button. **Saving assigns every story in the list an explicit rank matching its final position** — including a story that was only sitting there by date, not because anyone had pinned it — which is what makes "the story rank option on the News Dashboard can override the ranking in the story editor" literally true: both screens write the exact same columns, whichever was saved most recently wins.
- **Locking is what "important stories can stay in the key positions" actually means.** A locked row can't be dragged (its drag handle disables live the moment its Lock checkbox is checked, no reload needed) and is the one thing **Rank by Release Date** — the button that resets every *unlocked* story's rank back to null (falling back to date order) in one click — leaves alone. Locking only matters relative to those two mechanics; it doesn't change how a story sorts on its own.
- **Removing a story from a rotator (the Remove button, or "Not shown" in the Editor) and adding it back** both go through the same `home_excluded`/`sport_excluded` flag — re-adding always drops a story back in at "by release date" (clearing any old rank/lock it had) rather than guessing where to re-pin it, the same reasoning `_apply_due_publishes`-adjacent code elsewhere in this app applies: don't invent a position, fall back to the well-defined default.
- **A search box now sits next to the existing status/category/team/season filters on `/admin/news`**, matching against title, subheadline, and author name with a plain SQL `LIKE`.

## Staff Directory: a school-wide staff table, decoupled from roster attachment

This round built out `staff_members` into a real admin section and a public directory page, mirroring the existing Players/`athletes` pattern: one school-wide person record, separately attached to whichever team/season rosters via `roster_coaches`. The request was detailed and mostly unambiguous; the judgment calls made along the way are flagged below.

- **`staff_members` gained `first_name`/`last_name`/`title`/`email`/`phone`/`hidden_from_directory`**, replacing the old single `name` column. `team_id` and `is_head_coach` stay on the table but are now vestigial — kept only so the roster's inline quick-add form still has somewhere to write them on insert — `roster_coaches.team_id`/`roster_coaches.is_head_coach` (scoped per team + season, built in an earlier round) is what's authoritative everywhere the app actually reads from. Dropping those two columns outright felt like unnecessary migration risk for no functional gain, so they're documented as dead instead.
- **Staff Categories (`staff_categories`) are a single table for both sport and custom categories**, distinguished only by whether `team_id` is null. "One for every sport" is handled by `_ensure_sport_staff_categories()` — a lazy-ensure bootstrap (same pattern as the stats-feed token and Roster Settings elsewhere in this app) that creates a category row per team the first time anything touches `/admin/staff`, and keeps its name in sync with the team's own name on every read rather than storing a copy. Sport categories are locked against rename/delete from `/admin/staff/categories`, enforced server-side, not just hidden in the UI. Administration, Athletic Trainers, and Athletic Communications are seeded as the starting *custom* categories — same as any category an admin adds afterward, not a protected set.
- **A staff member's category placement is a separate, manual decision from their roster attachment** — checking a coach into their own sport's category on the Staff Directory does not happen automatically just because they're attached to that team's roster. This was the user's own explicit clarification mid-request ("the category they are assigned is only for the staff directory... staff will be assigned to rosters from the Coaches part of a roster"), so the two are deliberately decoupled: a school might not want every assistant coach listed under their sport on the public page, or might want a trainer cross-listed under a sport *and* under Athletic Trainers.
- **Two independent orderings exist**: `staff_categories.sort_order` (which section appears where on the public page — a plain HTML5 drag list at `/admin/staff/categories`, same vanilla-JS pattern as the News Rankings and Roster field-order screens, no external library) and `staff_category_assignments.sort_order` (who appears in what order *within* one section — a per-category drag screen at `/admin/staff/categories/<id>/order`, linked from each row).
- **Staff Directory Settings (`/admin/staff/settings`, `staff_directory_settings` table)** holds the intro text block for the top of the public page and a `fields_config` toggle list (Name/Title/Email/Phone/Social — enable/disable, customizable header text) — the exact same `{key, enabled, label}` JSON shape Roster Settings already uses for its Table display fields, reused rather than inventing a second pattern for the same idea.
- **The Staff Bio form** (`/admin/staff/new`, and inline on `/admin/staff/<id>`) covers every field asked for — First/Last Name, Title, Email, Phone, a repeatable Custom Fields list (same delete-and-reinsert pattern as an article's Related Links), Social Links (one-at-a-time add/remove, same as a Player's), category checkboxes, Bio, and the "Hide from Staff list" checkbox for a GA/student-assistant who should stay attachable to a roster without appearing on the public directory. A staff profile shows a read-only **Roster Assignments** table (mirroring a Player's Roster History) rather than a team picker on the form itself, since roster attachment is managed from that roster's own Coaches & Staff tab, not from here.
- **Head Coach career record**: the flag itself already existed (`roster_coaches.is_head_coach`, built in an earlier round). What's new is `_compute_coach_career_record()`, which aggregates every final, record-eligible (`counts_toward_record()`-passing) game across every team/season stint a person is flagged Head Coach for, and a Career Record card that only renders on a profile when at least one such stint exists. This inherits an existing limitation worth flagging: if a head coach changes mid-season, every game that season/team still counts toward whoever is flagged Head Coach *now* — there's no historical "who was head coach on this specific date" tracking.
- **The Coaches tab is renamed "Coaches & Staff"** everywhere it appears (Rosters hub, roster settings, the coaches-management screen itself), and its quick-add mini-form now takes separate First/Last Name inputs to match the new schema — this was an explicit request ("Should also change tha name to Coaches and Staff").
- **A "Staff Directory" link was added to the admin sidebar**, placed directly after Players and before Settings, and a "Staff" link was added to the public site's nav on every public page (`site_page.html`, `site_news_article.html`, `site_news_archive.html`), pointing at the new `/site/<school>/staff` page.

## Staff Directory round 2: direct feedback on the first pass above

- **Social Links couldn't be added on the New Staff form** — only from an existing profile, since the one-at-a-time add/delete forms need a real `staff_id` to post to and a brand-new person doesn't have one yet. Fixed the same way the Custom Fields repeater already handled this: a Platform+Handle repeater on `/admin/staff/new` (`social_platform[]`/`social_handle_or_url[]`, parsed by `_parse_staff_social_form` and bulk-inserted by `_save_staff_social_links` right after the new row's id exists) — an existing profile still uses the one-at-a-time forms, since by then there's somewhere real for each "+ Add Link" to post to.
- **Career Record can now take manual entries** (`staff_manual_records` — season, team/school name as free text, W/L/T, an optional note), additive to whatever `_compute_coach_career_record()` still derives from this school's own `roster_coaches` + `games`. This directly covers the two cases direct feedback called out: a season coached at a *different* school (computed can never see that — it only ever reads this school's own games table, now called out explicitly in a footnote on the card itself), and hand-correcting a season here where the single `is_head_coach` flag can't split a mid-season coaching change between two people. The Career Record card is now unconditional on every staff profile (not just current Head Coaches) specifically so the "+ Add a Season Record" form is reachable for someone who's never been flagged Head Coach at this school at all yet — a new hire whose whole career happened elsewhere, for instance.
- **Directory Settings can now surface custom fields** (`staff_directory_settings.custom_field_labels`, a JSON array of label strings) — since `staff_custom_fields` is genuinely freeform per person with no fixed schema, there's no per-school toggle to hang off a key the way Name/Title/Email/Phone/Social already work. Instead, an admin types the exact label text they want surfaced (e.g. "Alma Mater," "Grad Year," "Office Location") and any staff member with a custom field matching that label (case/whitespace-insensitive) shows it on their public card — deliberately still not a fixed category anywhere, matching the request that these "aren't default categories anywhere and shouldn't be."
- **Deleting a staff member is gone entirely** — there's no delete route left at all, not gated behind a role check, since the ask was explicit that this shouldn't be possible "regardless of access." `staff_members.active` (default 1) replaced it: deactivating takes someone off `/admin/staff`'s default list and the public directory without touching anything else about their record (roster history, custom fields, social links, career record all stay exactly as they are), and reactivating brings them right back. `/admin/staff` defaults to Active with a status dropdown (Active/Inactive/All) to see everyone else.
- **A second public template**: `staff_directory_settings.directory_template` (`cards` | `table`), a dropdown on Directory Settings. Cards is the original photo-forward layout; Table is a plain, dense listing with no images at all, columns driven by the same Fields Shown toggles plus any configured custom field labels — for a school that doesn't want to lean on headshots. Same underlying `sections`/`fields_config` data either way; `site_staff_directory.html` just branches on which to render.

## Byline bug fix + a new per-user default

Direct feedback: clearing the Author/Byline field on a story and saving still showed the logged-in user's name on the public page. The actual bug was in `_parse_article_form` — `f.get("author_name") or CURRENT_USER["name"]` ran on *every* save, not just a brand-new story, so an intentionally-blanked field got silently overwritten with the current user's name again on save. Fixed by dropping the fallback from the save path entirely (blank now saves as `NULL`, and the public template's existing `{% if article['author_name'] %}` check already skips the "By " line for that case) and moving the *only* legitimate default — prefilling a brand-new story's form — to where it belongs: `_article_form_context`, gated by a new `users.show_byline_by_default` column (default on). `/admin/users` gained a Byline Default column with an On/Off toggle per person, using the same "matched by name, no real session" lookup (`_current_user_row`) that `_current_user_permissions` already established as this prototype's stand-in for real auth.

## Packaged for a durable, password-gated demo deploy

The prototype only ever ran under Flask's own dev server (`app.run(debug=True)`), which isn't meant to sit behind a real URL, and had no access control at all — anyone with the link is a full admin, since there's no login system yet (see "No auth" below). To let someone offsite click around on a link that stays up for days/weeks and surface things that need improvement, three small additions make it deployable as-is to any host that runs a standard Python web app (Render, Railway, Fly.io, etc.), with no code changes needed per-host:

- **`Procfile`** — `web: gunicorn app:app --workers 1 --bind 0.0.0.0:$PORT`, the standard production WSGI entrypoint most Python hosts look for automatically. Deliberately pinned to a single worker: with only one process ever starting cold, the auto-seed step below can never have two workers racing to seed the same brand-new database at once.
- **Cold-start auto-seed** (top of `app.py`) — if `dev.db` doesn't exist yet when the app starts (a brand-new deploy, or a host whose disk got wiped), it calls `seed.run()` automatically, the same seeding this prototype has always used locally. If `dev.db` already exists, nothing is touched — so a host restart or wake-from-sleep doesn't wipe out anything a tester added or edited during the demo.
- **`DEMO_PASSWORD`-gated Basic Auth** (`_require_demo_password`, a `before_request` hook in `app.py`) — set a `DEMO_PASSWORD` environment variable on the host and every route, admin and public, prompts for it via a plain browser login dialog before serving anything. Leave it unset (the default for local dev) and nothing changes — the gate simply doesn't run.
- `requirements.txt` gained `gunicorn`.

All three were tested locally: a fresh run with no `dev.db` present confirmed the auto-seed fires exactly once and the site comes up seeded; a run with `DEMO_PASSWORD` set confirmed no-credentials and wrong-password requests both get a 401 on both `/admin/...` and `/site/...` routes, and the correct password lets requests through normally.

One honest caveat: exactly how long a free-tier host keeps `dev.db` around (across the service sleeping/waking vs. a fresh redeploy) depends on that host's specific disk behavior, which hasn't been verified against a live hosting account from here — worth confirming once the demo is actually up.

## Postgres support, for hosts with no persistent local disk (Vercel)

The demo deploy above assumes a host like Render that gives the process a real, persistent disk `dev.db` can live on. A serverless host — Vercel specifically, since that's the account already connected for this project — has no such thing: every request can land on a fresh instance with an empty filesystem, so SQLite can't follow this app there at all. Setting a `DATABASE_URL` (or `POSTGRES_URL`, the name Vercel's own Postgres/Neon storage integration tends to inject) environment variable switches every connection in the app to real Postgres instead; leaving both unset keeps every existing SQLite behavior exactly as it was, so this is purely additive.

- **`db.py`** now holds a small compatibility layer so the ~260 call sites elsewhere in `app.py` that were written against sqlite3's conventions — positional `?` and named `:key` placeholders, dict-like `Row` access, `cursor.lastrowid` after an INSERT, `executescript()` for the schema file — needed zero changes. `_translate()` rewrites placeholders to psycopg2's `%s`/`%(key)s` (and `INSERT OR IGNORE` to `INSERT ... ON CONFLICT DO NOTHING`, used by `seed.py`); `_PGCursor` emulates `lastrowid` by appending `RETURNING id` to an INSERT, but only against a table that actually has one — `_tables_with_id_column()` reads `schema.sql` once to know that `staff_directory_settings`, `roster_settings`, `schedule_settings`, `permissions`, and `role_permissions` use a natural key instead and don't.
- **`schema.sql`** itself needed one real fix, not just a Postgres-vs-SQLite translation: `game_player_stats.athlete_id REFERENCES athletes(id)` was declared *before* `CREATE TABLE athletes` later in the file. SQLite tolerates a forward reference like that within one `executescript()` batch; Postgres does not — the referenced table has to already exist. Moved the whole `athletes` table definition earlier, ahead of `game_player_stats`. The Postgres-specific spelling differences (`INTEGER PRIMARY KEY AUTOINCREMENT` → `SERIAL PRIMARY KEY`, dropping the SQLite-only `PRAGMA foreign_keys` line) are handled automatically, in `db.py`, at schema-load time — there's still only one schema file to maintain.
- **`app.py`'s cold-start auto-seed** had to become backend-aware too: the existing "does `dev.db` exist" check is meaningless for Postgres (that path never exists regardless of the real database's state), and naively reseeding on every process start would be actively harmful on a platform that cold-starts as often as Vercel does — it would fire `CREATE TABLE` against an already-seeded database on nearly every request. It now asks Postgres directly (`SELECT to_regclass('schools')`) and only seeds the one time that comes back empty.
- **`requirements.txt`** gained `psycopg2-binary`. **`vercel.json`** tells Vercel's Flask framework preset where the app instance lives (`app.py`, matching its own docs' example).

**How this was actually tested**, given this environment's own network policy blocks installing psycopg2 here: the full schema (after `db.py`'s automatic Postgres translation) was run against a real local Postgres 16 server — this is what caught the `athletes` forward-reference bug and a second real bug (blindly appending `RETURNING id` to every INSERT, which fails outright against the five tables with no `id` column, caught the same way). The placeholder-translation logic itself is pure Python with no psycopg2 dependency, so it has direct unit tests. And `seed.py` — several hundred real INSERT/executemany calls, exercising most of the schema — was run end-to-end through `db.py`'s actual, unmodified code against that same real Postgres server, via a throwaway stand-in for the psycopg2 module that shells out to `psql` instead of speaking the wire protocol (not something to ship — just a way to actually execute this code against a real database from a sandbox that can't install the real driver). That run completed cleanly. A full sweep of every page over HTTP was attempted the same way, but that stand-in's driver can't tell a real Postgres `INTEGER` column from a `TEXT` column that merely contains digits (e.g. `games.season`, stored as `'2026'`), so it wrongly guesses those into Python ints and then fails a real type check Postgres enforces — confirmed by inspecting the source that `season` is written as a literal string everywhere (`seed.py`) and never cast to `int`, so this is a limitation of the stand-in, not a bug in the app. The real, authoritative version of this last check — the live app, real psycopg2, real Postgres — still needs to happen against an actual deployment; local SQLite behavior was re-verified unchanged (all 49 smoke-tested routes) after every change in this section.

**What's still needed, outside this codebase, before this can go live**: a Postgres database actually has to exist somewhere for `DATABASE_URL` to point at. On the Vercel account already connected to this project, that's the Storage tab → Connect Database → Neon (or another Postgres provider) → free plan, which auto-injects the connection env var into the project once linked — no code change needed on this end to pick it up.

## Game Central — a permanent page for every game

Direct ask, styled after ESPN's Gamecast: every game on the schedule should have its own real page covering the whole lifecycle — links, articles, box scores, location — before, during, and after. Worth flagging up front: an earlier round built a full real-time "Live Game Center" (drive chart, play-by-play ticker, 20-second polling) and then explicitly tore it out in favor of partnering with a real stats provider for the in-game experience (see "The pivot" above). Confirmed directly before building this that it wasn't meant to reopen that decision — Game Central is a static-on-load hub page, not a live-refreshing one; the score/status it shows is exactly what the stats webhook already keeps current, it just doesn't poll for it client-side.

- **`/site/<school>/games/<id>`** — every game gets this automatically; there's no "create a Game Central page" step anywhere in the admin. It's assembled entirely from data the box-score, story, and schedule systems already produce: `_enrich_game()` (unchanged) supplies the team stats/scoring plays/player stats, a new `_load_game_story_article()` pulls a published preview and recap by category (`game_preview`/`game_recap`) rather than the schedule modal's existing "whichever published most recently" rule — the two needed to be kept distinct so a team that posts both doesn't lose the preview the moment a recap goes up. Registered ahead of the generic `/site/<school>/<page_slug>` catch-all the same way `/news/<slug>` already is.
- **Layout went through three passes.** The first pass was a tabbed, ESPN-Gamecast-style shell (Recap/Preview/Story, Box Score, Game Info as separate tabs). Direct feedback with a reference screenshot (a magazine-style boxed layout — matchup strip, a story teaser card, a Leaders box and Series History side by side, a Game Information sidebar) replaced that with a flowing, no-tabs page. A third pass, from a real athletics-website reference screenshot plus starter HTML/CSS, added: real win-loss records in the matchup strip and a row of Watch Live/Live Stats/Tickets action buttons beneath it (whichever of `livestream_url`/`box_score_url`/`tickets_url` this game actually has — same "only show what's real" rule as the sidebar's matching text links); a three-across **Season Snapshot** box alongside Leaders and Series History, reusing `compute_record_bar()` (the same function behind the schedule page's Record Bar) rather than tracking anything new; a two-across **Last Time Out** / **Up Next** row (the team's most recent completed game and next scheduled one, via two new query helpers, `_load_last_time_out`/`_load_up_next`); and a **Recent Stories** grid at the bottom reusing the Sport page's News rotator query, scoped to this game's team and minus whichever article is already shown as the page's own story teaser. Pregame and postgame still share the same skeleton — postgame just adds the full Team Stats/Scoring Summary/Player Stats tables beneath the small-box rows. The matchup strip always reads away-team-left, home-team-right regardless of which side is this school's own team; "our" side always uses the site's own initial-badge mark (this prototype's schools have no logo asset of their own, only opponents do).
- **Several boxes needed direct decisions on scope, confirmed before building each time**: a **Series History** box (head-to-head record vs. this opponent) has no data behind it — ships as a labeled "coming soon" placeholder rather than invented numbers. A **Leaders** box (this game's top performer per stat category) *is* real, computed by `_compute_game_leaders()` from the same per-game player stats the box score already has — but only for a sport with player-stat categories defined at all (football today), same "absent, not a disabled stub" rule every other sport-gated feature in this app follows. The third pass's reference had three more asks with no data behind them, each confirmed rather than faked: a **Game Notes** box (free-text bullets like "Redhawks are 4-1 at home") has no schema anywhere for admin-authored game notes, so it's left out entirely, not even a placeholder; a **National Rank** line in Season Snapshot is left out the same way, since no poll/ranking is tracked for any team; and the matchup strip shows a real record for this school's own team only — opponents here are just names/logos we play against, not tracked teams with a full season of their own, so there's no real opponent record to show without fabricating one. A venue photo in Game Information was also confirmed as out of scope — `games.facility` is a name string only, no photo field exists.
- **Reachable from every schedule view, not just one.** Direct ask: "a Game Central button on each game," with placement expected to vary by how much room each view actually has. Matchup Cards, Timeline, and Season Story's featured Next Game card get a full "Game Central →" text link; Classic Athletics, Compact List, and Season Story's upcoming-games strip/month lists get a compact arrow-only version instead, since those rows don't have room for a full label. Calendar's day cells are tight enough that even the compact version doesn't fit, so those stay reachable the same way every view already was — through the existing click-to-open modal, which now also leads with a "Game Central" link (promoted to the modal's primary action; the rest, including "Read Recap," moved to secondary styling). The existing click-to-open-modal behavior itself is untouched — this is additive on every view, not a replacement.
- **The two other places a game already showed up now link to Game Central too**: a recap article's "Recap of [game]" callout on its public story page gained a "View Game Central →" link, so the two pages point at each other.
- Respects the same "future schedule not public yet" gate the full schedule list already does (`schedule_settings.hidden`) — a game's permalink can't reveal a season before an admin means to, even if someone guesses or shares the URL early. Verified directly: hiding a team's season 404s that team's game pages while leaving every other team's games unaffected.
- Tested against all 31 seeded games across every sport/status combination on file (upcoming, live, final, with and without stat categories, with and without a linked article) with Flask's test client in exception-raising mode — all returned 200 with no template errors, re-verified after each of the three layout passes. Also screenshot-checked with a headless browser against real seeded data (a pregame football game, a final football game with a full box score and computed leaders, a live football game mid-webhook-push, and a soccer game with a real recap article) — caught and fixed two real rendering bugs this way: a CSS specificity bug where the story teaser's headline inherited the plain card-header bar's background/padding from a shared `.gc-card h2` rule (fixed with a more specific override), and, in the third pass, the Leaders box's name/value row wrapping illegibly once that box went from half-width to a third-width (fixed by stacking the stat label above the name/value line instead of one crowded row) plus a same-line score ("W 27–24") breaking mid-number in the narrower Last Time Out card (fixed with `white-space:nowrap` around the result+score together).

## What's stubbed or missing (Phase 1 still has more in it than this)

- **No auth.** `CURRENT_USER` in `app.py` is hardcoded to Sarah Jennings/Admin. Real login, sessions, and permission-checking middleware aren't built — so right now every visitor to `/admin` effectively has Admin access, with no scope enforcement from `user_team_scopes`.
- **Pages are still read-only.** Schedule and Rosters both now have full add/edit/delete; the Page Builder (no drag-and-drop block editor) hasn't been built out the same way yet — same query pattern, just not done.
- **Roster still isn't its own dedicated public page** (unlike Schedule, which got split out from the team hub page into `/site/<school>/teams/<team>/schedule`) — it's still one inline block on the team hub page, now with three display varieties (Card/Photo/Table, admin-chosen per team, see above) instead of just one fixed look. A visitor-facing switcher like Schedule's, a dedicated Roster page, and individual player bio pages with their own URLs are all still open, whenever that's the next thing to tackle.
- **Pages/blocks are seeded, not built in-app.** `seed.py` inserts the Home and Men's Soccer pages directly. A real Page Builder UI (add/reorder/edit blocks) is future work.
- **No Media or Sponsors admin screens yet** — Rosters, Schedule, Users, Pages, News, and now the Staff Directory were built first as the representative slice; the same query pattern extends to the rest.
- **The Story System now has a real rich-text editor (see above) but still no image upload, related-content picker, or version history** — Featured Image, inline body images, and Related Links are all URLs typed/pasted by hand, not picked from the system, same as every other image field in this prototype (see the deferred Media & File Library in "Deliberately not built in this pass" above). Editing and re-publishing an article overwrites it outright — there's no draft-vs-live diff or edit history. The News Archive also has no pagination yet (it lists every published article on one page), fine at this prototype's scale but not built to grow indefinitely. Template Type is a placeholder with exactly one real option (Standard Article) — building out additional public templates is explicitly future work.
- **Live Stats / stats-feed webhook is deliberately narrow so far**: the parser targets a real vendor format (PrestoSports' `<fbgame>`, see the dedicated section above) but only against one real completed-game sample — the webhook's live-push handling and "live" vs. "final" status inference haven't been checked against a real in-progress export yet, only simulated. The webhook's `token` is an unguessable-URL convention, not real auth (see "No auth" above) — there's no request-signing, no IP allowlisting, and no rate limiting on the endpoint. No season-long cumulative stats or leaders pages (single-game only — team totals, scoring plays, and player lines all reset per game), no kicking/punting/return-yardage player categories, and no sport besides football has `TEAM_STAT_CATEGORIES`/`PLAYER_STAT_CATEGORIES` entries yet. The full play-by-play is still parsed and stored in `game_plays` but nothing displays it any more (only scoring plays do) — there's no *real-time* fan-facing in-game experience now that the Game Center is gone, on purpose (see "The pivot" above): that's meant to come from a real live-stats provider partnership instead. The game-card modal and Game Central (see above) both show a completed or in-progress box score exactly as of page load, never a live-updating one, even though the score itself does update live via the webhook. (Don't confuse "Game Center," the removed real-time page, with "Game Central," the new static-on-load permalink described above — similar names, deliberately different scope.)
